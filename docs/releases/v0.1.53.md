# v0.1.53 — REALITY SNI guard (anti traffic-theft)

Every REALITY inbound now has an in-agent TCP front end that filters TLS
ClientHellos by SNI before Xray sees them. This closes the traffic-theft path
described in the official Xray REALITY documentation, where a connection that
fails REALITY authentication is forwarded to the configured dest and the
attacker's own SNI is replayed verbatim. If that dest is a CDN node that routes
by SNI instead of validating it, the attacker obtains a proxy to an arbitrary
target through your node.

## What changed

- A guard listener owns each REALITY inbound's public port. It parses the
  ClientHello, allows only the inbound's declared `server_names`, and drops
  everything else without dialing the dest. Non-TLS traffic, malformed
  handshakes and hello messages without SNI are dropped too.
- SNI matching is exact and case-sensitive, mirroring the REALITY server's own
  `server_names` map lookup, so a casing difference cannot slip past the guard
  only to land in the fallback path anyway.
- Xray's REALITY inbound now binds loopback behind the guard. On transports
  that support `accept_proxy_protocol` (TCP, WebSocket, HTTPUpgrade) the guard
  prepends a PROXY-protocol v2 header, so access records and per-IP limits keep
  the real client address. On gRPC and XHTTP, which have no proxy-protocol
  support in this Xray fork, the header is omitted and the recorded client
  address is loopback.
- All declared `server_names` now reach Xray. Previously only the first entry
  was propagated, so a client dialing any other declared name fell through to
  the fallback path even with the guard in place.
- Guard lifecycle follows configuration: applied on `ApplyConfig`, rolled back
  with the core on failure, retired when an inbound is disabled or removed, and
  the public port is released. Loopback backend ports stay stable across
  config re-applies so live users are not reshuffled.
- The heartbeat now reports `guarded_inbounds` and `guard_rejected`, so the
  control plane can see how much non-declared SNI is being dropped.

This applies to every REALITY inbound on the node, whether it was configured
before this release or added afterwards. Enrollments and existing
`vless + reality` configs need no change.

## Operation

`MNET_REALITY_SNI_GUARD=off` in the agent environment disables the guard and
restores the previous direct-listening behavior. It exists as an escape hatch
for operations only; leaving it unset keeps the protection on.

## Notes and limits

- NAT, port-forwarding and telnet-level proxies in front of the node are
  unaffected: the guard sees whatever TCP peer reaches it.
- Only the SNI is inspected. A client that presents a declared SNI is still
  forwarded to REALITY, which then applies its own authentication; the guard
  does not weaken REALITY's own probing resistance, and non-declared SNI no
  longer produces a distinguishable fallback response through this node.

Validation: full Go tests and vet, including guard unit tests (forwarding,
case sensitivity, malformed input, PROXY-protocol address preservation) and
runtime integration tests (guarded inbound, allowlist rotation, port release).
The release workflow re-runs tests and builds Linux amd64/arm64.
